# Dark NULL v2 Build Plan (PLAN_2027)

status: plan. Companion to [`DESIGN_2027.md`](./DESIGN_2027.md) and
[`CLAIMS_POLICY.md`](./CLAIMS_POLICY.md). Written 2026-10-06. Phase 0 spikes measured 2026-10-06:
[`PHASE0_RESULTS.md`](./PHASE0_RESULTS.md).

Every phase ships on devnet. Each phase lists:

- deliverables;
- tests;
- the devnet demo;
- gates, which must pass before the phase counts;
- kill rules, which say what changes if a gate cannot be met;
- what may be shown, per CLAIMS_POLICY.md.

Effort is in engineer-weeks [E].

## 0. Ground rules for the build

- **Supply chain.** No package installs and no builds of ported or new code on a workstation that holds
  live keypairs. All `cargo`, `npm` and circuit builds run in CI or a sandbox VM.
  - npm installs use `--ignore-scripts`.
  - New crates (sonobe, arkworks 0.6, circom witness tooling) are pinned by lockfile and reviewed before
    first use.
- **Identity.** The program id comes from the network config (`NETWORKS.json`, SDK cluster config) and
  is never hardcoded in docs or clients. The v2 program gets a fresh keypair, generated in the sandbox
  and never committed.
- **Artifacts.** Every circuit, proving key, verifying key and program binary is hash-bound in
  `MANIFEST.json`. Partial promotion is a bug, which is the existing rotation rule in
  `docs/zk_conventions.md`.
- **Claims.** A test or benchmark is cited by commit. Re-run after the last change.

## 1. Phases

### Phase 0: specification and test vectors (2-3 eng-wk)

**Deliverables**
- `docs/spec/V2_SPEC.md`: keys, `DS_*` registry, byte encodings, note, nullifier, `sighash`, `pi`,
  `ext_data` layout, circuit statement, program ABI, x402 scheme payloads.
- `vectors/v2/*.json`:
  - V-POS: Poseidon for 1-12 inputs;
  - V-NOTE, V-NF, V-SIGHASH, V-PI, V-EXTDATA, V-VOUCHER, V-ADDR.
- Crate `crates/dark-null-transcript` (ported, section 4) with the prover-malicious harness.

**Spikes** (each ends in a committed result file under `bench/results/p0/`)
- **S-TXV1.** Send a ~1.4 KB Transaction V1 to devnet through public RPC and record acceptance.
- **S-PLONK.** Verify a PLONK and an fflonk proof of a test circuit on devnet and record CU and size.
- **S-NULL.** Measure CU and rent for nullifier options A and B (DESIGN 7.4). Document option C's fees.
- **S-PROVER.** A pure-Rust Groth16 prover on a 2^16 test circuit on macOS, Windows and Linux.

**Tests and gates**
- G0.1: V-POS outputs are identical from circomlib (witness), light-poseidon (Rust) and `sol_poseidon`
  (a minimal devnet test program). **Passed 2026-10-06:**
  - 24/24 V-POS cases identical across all three plus circomlibjs;
  - 10/10 derivation vectors on chain;
  - evidence in PHASE0_RESULTS section 5.
- G0.2: S-TXV1 result recorded, either way. **Recorded 2026-10-06:** V1 is accepted end to end up to 4,096 bytes
  (PHASE0_RESULTS section 1).

**Spike results (2026-10-06).**
- S-TXV1: V1 accepted.
- S-PLONK: PLONK verify 328,447 CU, fflonk 1,195,874 CU, Groth16 81,282 CU.
- S-NULL: option A 1,727 CU and 650,240 lamports per nullifier; option B 111-217 CU and 164,846 lamports per slot.
- S-PROVER (native Groth16, 4 vCPU):
  - skeleton: 23,155 constraints, p50 260 ms;
  - full-size proxy: 40,914 constraints, p50 433 ms;
  - circom + snarkjs PLONK skeleton: 73.6 s.

Still open in P0:
- `docs/spec/V2_SPEC.md` with the final `DS_*` registry;
- V-EXTDATA, V-VOUCHER and V-ADDR;
- the `dark-null-transcript` port.

**Kill rule.** If V1 transactions are not accepted end to end, P1 uses legacy transactions with a
compressed proof and a lookup table. DESIGN 7.8 already covers that fallback.

**Devnet demo.** A transaction whose `sol_poseidon` output equals V-POS.

**What can be shown.** "v2 specification and cross-implementation test vectors."

### Phase 1: shielded pool v2 (10-14 eng-wk)

**Deliverables**
- `circuits/transact_v2.circom`, the universal circuit with every branch compiled in. P1 enables only
  the principal branch for deposit, transfer and withdraw; the other branches are rejected by program
  config.
- `programs/dark-null-pool-v2`: Anchor, zero-copy. Instructions per DESIGN 7.1; nullifier option A.
- `crates/dark-null-client` (builder, prover, scanner) and `crates/dark-null-signer` (in-process
  signing, Python bindings).
- Relayer mode added to the existing swarm (`swarm/server.mjs`).
- `dev-setup` Groth16 keys, labelled as such in `MANIFEST.json`.

**Tests**
- Privacy and shape:
  - P-UNLINK: no public field of a spend equals or is derivable from its deposit;
  - P-AMOUNT: in-pool transfer transactions carry no amount;
  - P-SHAPE: identical size and account list across kinds.
- Program correctness:
  - T-SOLV (supply counter and vault invariant);
  - T-ROOT (on-chain root equals the client root; root hint mismatch rejected);
  - T-REPLAY (same proof rejected; same nullifier rejected);
  - T-FR-CANON (non-canonical scalars rejected);
  - X-RELAY (each `ext_data` field mutation fails verification).
- Mint guard: Token-2022 mints with forbidden extensions are rejected.
- Malformed proof corpus (extends `tests/malformed-proof.test.mjs`).
- Fuzzing of instruction parsing.

**Devnet demo.** Three wallets: deposit, a private transfer, then a relayed withdraw to a stealth
address. Every signature is listed in `bench/results/p1/`.

**Gates**
- B2: transact at most 400k CU, and the transaction fits V1 (or the legacy fallback).
- B1: prover p50 at most 3 s and peak RAM at most 2 GB on the reference laptop.
- All P1 tests listed above pass.

**Kill rules**
- If B2 exceeds 1.0M CU: split into `verify_and_record` and `insert_and_pay` instructions in one
  transaction.
- If B1 p50 exceeds 6 s: drop the always-present channel and association branches into a second circuit
  and document the shape leak.

**What can be shown.** Unlinkable deposit-to-withdraw on devnet; hidden in-pool amounts; arbitrary
amounts; measured CU and proving time; trustless on-chain root.

### Phase 2: private x402 payer (4-6 eng-wk)

**Deliverables**
- dna-x402 changes, listed in DESIGN 6.5:
  - the `dark-null-exact` scheme;
  - `DarkNullVerifier`;
  - the `ReceiptPayload` fields;
  - salted recipient hashes;
  - client `payPrivate`.
- The local core binary (`dark-null-core`) with the localhost API subset from DESIGN 12.7: health,
  accounts, sync, balance, builds, `x402/exact`, signatures, submit, freeze, receipts.
- Feature flags `devnet-only` (default and only build) and `x402_enabled` (default off).

**Tests**
- X-BIND: a mismatched quote binding is rejected by the merchant verifier.
- X-REPLAY: the same `cm0` cannot unlock twice.
- X-RCPT: the receipt contains no raw payer, recipient or transaction-to-identity mapping.
- API tests: every error code in DESIGN 12.7 has a test; Host-header and token checks; genesis check
  refuses non-devnet RPC.
- C-CONSENT: no endpoint can produce a submitted spend without a signature from `dark-null-signer`.

**Devnet demo.** An agent pays a demo paid API through `dark-null-exact`. The merchant verifies,
serves, and returns a signed receipt. The demo is replayable from the script.

**Gate.** The end-to-end run is recorded with signatures, and B6-lat for exact mode is measured.

**What can be shown.** "Agents pay x402 endpoints from a shielded balance on devnet; receipts bound to
x402 quotes."

### Phase 3: session channels and per-epoch settlement (6-8 eng-wk), plus folding accountability (6-10 eng-wk, gated)

**Deliverables (channels)**
- Channel and policy branches enabled in the program.
- The `dark-null-batch` scheme in dna-x402.
- Voucher endpoints in the core.
- Rolling close; receipt-chain head anchoring; conditional payments.
- Nullifier store option B or C, selected by S-NULL/B3.

**Tests (channels)**
- CH-*: over-cap voucher rejected; non-monotone voucher rejected; merchant close after expiry rejected;
  agent reclaim before expiry rejected; double close rejected; rolling close conserves value.
- POL-*: per-payment cap; allowlist; expiry; change must return to the policy owner; agent withdraw
  flag; revocation by the principal.

**Deliverables (folding, ported)**
- `crates/dark-null-fold`. The agent folds its two-signed receipt log into a spend-accountability proof:
  total spent, count, per-merchant totals, policy compliance.
- The principal or a scoped viewer verifies it off-chain. Nothing goes on-chain (DESIGN 11.1).

**Folding gates**
- F1: fold cost at most 50 ms per step, with a stretch target of 10 ms. Prior internal research measured
  about 340 ms per step, unoptimized.
- F2: peak RAM at most 1 GB.
- F3: off-chain verify under 1 s.

**Folding kill rule.** If F1 exceeds 100 ms after optimization, ship log-based summaries instead (the
verifier replays the two-signed log directly) and park folding.

**Devnet demo.** An agent makes 1,000 paid calls to one merchant in one epoch. There is one open and one
close on devnet, and the B3 row is produced from the run.

**Gate.** The B3 table at N = 10, 100 and 1,000, with nullifier storage cost included.

**What can be shown**
- "One on-chain settlement per merchant per epoch."
- The measured per-payment cost.
- "Agent spend limits enforced inside the proof."
- Folding wording only after F1-F3 pass.

### Phase 4: association sets and viewing keys (5-8 eng-wk)

**Deliverables**
- Label rules in `transact_v2`.
- `post_assoc_root`, the ASP registry, the ragequit circuit and instruction.
- `ciphertext_rec` scoped disclosure records and `POST /v1/viewing-keys`.

**Tests**
- B4: member withdraw succeeds; non-member withdraw fails; ragequit succeeds without an association

- VK-SCOPE: a key for period p and agent a decrypts only p and a.
- VK-VERIFY: a holder verifies every in-scope spend against chain state without spend keys.

**Devnet demo.** An ASP posts a root, a member withdraws, and a revoked deposit ragequits. All
transactions are replayable.

**What can be shown.** "Association-set membership proofs on Solana devnet, with ragequit"; "scoped
viewing keys".

## 6. Top risks

1. **Nullifier storage cost.** It dominates the batch-mode economics (DESIGN 7.4). Mitigation: S-NULL in
   P0, then option B or C.
2. **Setup trust for mainnet.** Phase 0 measured PLONK verify at 328,447 CU but PLONK proving far over B1.
   Mitigation: plan the public Groth16 phase-2 ceremony (setup track) and keep R-PLONK-PROVER as research.
3. **Public-leg amount and timing leaks.** These deanonymize users regardless of circuit design
   (DESIGN 3.3). Mitigation: SDK defaults, in-pool merchant settlement, and B6 measurement.
4. **Universal-circuit proving time on laptops** with every branch present. Phase 0 measured the full-size proxy at
   p50 433 ms (4 vCPU) and 1,291 ms (1 thread) with native Groth16. Mitigation: re-measure B1 on the reference
   laptop and in a browser in P1; the two-circuit fallback stays available.
5. **Consent semantics for batch mode** with the runtime lane (D-CONSENT). Mitigation: decide before P3;
   exact mode works without it.
